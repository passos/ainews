## Remote-read-only: first-hand research by a reader authorized by root

For each candidate, use at most the official directory, robots, the feed / list, and two body samples. Prefer one each from Education, Fed and NIST. Do not use production secrets. Do not call models. Do not write to production. If a redirect leaves to an unreviewed domain, record the new host and stop. Do not follow it. Do not search without bounds.

1. Take the actual RSS/Atom link from the official directory. If there is no RSS, check that the server returns an HTML list. Record the UTC time, the final URL, the host of each hop, the content-type, the parse result, the date field, the update cadence, the sample URLs and the terms link. Do not paste unknown query tokens or credential URLs. Do not guess endpoints.
2. Check robots/crawl-delay for the list and the body with the project UA `DailyBot/1.0 (+https://news.ioenv.com)`. If permission is missing or the check fails, do not work around it. The existing collect step does not check robots for RSS feeds. It checks robots for HTML. So the RSS case does not let you skip the body compliance check. This task does not change that policy.
3. The two body samples must work without a browser or Jina and without crossing a paywall. They must meet the existing `isBody` and the 2MiB limit. Record the body rung. Do not set summaryIsBody on a summary feed on your own. A CSS selector must be verified against the real DOM. List each body / redirect host that waits for review. SEC data keeps using the existing edgar client.
4. Validate the dossier with the strict SourceConfig validation in `src/pipeline/collect/config.ts`. The owner checks the list, the section assignment, the domains, the frequency, the thresholds and the expected incremental cost. First keep the existing review and thresholds, and add only a few candidates. An automatic discovery policy is not authorization for manual source onboarding.

## Owner-mutation: manual onboarding, activation, pause

The existing Access admin `createSource` (POST) writes `sources.status='candidate'`. `approveCandidate` reads a different table, `source_candidates`. You cannot pass a manual source id to it. The existing protected POST `resumeSource` can activate sources, but the UI shows Resume only for paused sources. So do not claim that a manual candidate has a complete UI loop. Do not turn on discovery to get around this.
Recommended: the owner approves a single-row conditional SQL and the counts before and after. Alternative: authorize an operator to use the existing Access-protected resumeSource (check the id and status first; do not guess the server function id). Or a #9 follow-up adds the UI (deferred). Until a channel is chosen, run SELECT only. Also, no general admin helper for pause was verified. Do not invent an interface. Do not delete history.

The following are only binding templates that wait for review. **Do not paste them directly into Wrangler.** The parameters must come from a specific approved dossier and from a real SELECT. The owner first picks a controlled channel that supports binding, or approves an absolute-path SQL file with the concrete values already substituted. Then run it once. ?1 is not a bound source id.

```sql
-- Owner-approved activation, expected affected rows = 1.
UPDATE sources SET status='active' WHERE id=?1 AND industry_id=?2 AND status='candidate';
-- Owner-approved pause, expected affected rows = 1.
UPDATE sources SET status='paused',paused_reason=NULL WHERE id=?1 AND industry_id=?2 AND status='active';
```

Before the change, query the target id/industry/status/count. After it, check id/status/count with an independent read-only query. If it affects 0 or more than 1 row, stop. Do one approved source at a time. Never run an UPDATE on all candidates in the table. Activation keeps interval/config. Scheduling produces model cost, so the expected incremental budget must be approved. Pause does not touch body or review history. Root observes real collection, analysis, current-body manual approval and public output. A failure leaves a fixed health category. Do not auto-refill the queue, lower thresholds, switch to auto, turn on Jina, or swap in a broad aggregator source.

The owner may: approve the candidates above after research (recommended), name a replacement, or keep the section empty. The last choice does not block local code, but M4 cannot be accepted. Reuse the thresholds as recommended. Review any change separately. A new Industry domain and the activation channel each need their own specific approval. Each of the four sections needs an active real source, a successful fetch in the current period, current manually approved articles, and a non-empty section/RSS. One last_ok_at does not prove 24h of continuous operation. See [Deployment and evidence gates](deploy.md). Without the original artifacts, mark it unknown.
