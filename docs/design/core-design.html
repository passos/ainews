多行业热点站：自己找信源、自己写日报

参考 AIHOT 的主干（采集 → 模型筛选与写作 → 归组成事件 → 日报 → 网站与 RSS），搬到 Cloudflare 上：一个 Worker、D1、Queues、AI Gateway、Browser Run。一个管理员可以在后台增加行业，每个行业的信源可以手动添加，也可以让 AI 搜索、探测、评估后列为候选。

和 Newsren 计划书的关系：计划书的方向是"面向读者的研究代理"。ainews v1 做它的 Stage 1，再加上 Stage 2 的批量版：Brief 和分读者解释在文章入选时就生成好，读者不会触发模型调用。要不要往前一步，看 Q11、Q12。

01 · 与 AIHOT 的三个根本差异
行业 = 运行期数据

AIHOT 的 industry/（分类、提示词、门槛、示范信源）是部署期代码，一个部署一个行业。ainews 把它们变成 D1 里按 industry_id 分区的行，在后台新建和编辑，评分提示词是数据，不是代码。

三进程 + Postgres → 一个 Worker

web / api / worker 三个进程和 pg-boss 队列，变成一个 Worker 的三个入口：fetch（网站、RSS、后台）、scheduled（定时）、queue（采集、分析、归组）。D1 没有锁和交互式事务，串行化另找办法（见 06）。

信源可由 AI 发现

AIHOT 的信源由人写进 sources.json。ainews 增加发现流程：起草搜索词 → Web Search API → 探测 RSS 或列表页 → 抽样评估 → 进候选列表，管理员批准后才开始抓取。

04 · 继承的不变量

AIHOT 里对所有站都成立的规则，原样保留

读者打开页面不触发模型调用
模型只在 queue 与 scheduled 入口里调用。fetch 入口的代码路径不 import 模型模块，用一条架构测试扫 import 来守住。如果 Q11 选了做 Ask，提问也只是进队列，由 queue 入口回答。
抓取只对批准过的地址
正文抓取梯（见 07）只抓已批准的信源，加上每个板块一手来源白名单里的域名。读者提交的 URL 不抓，也不做无限制浏览。
所有公开出口只从一个读取层读
src/publication/ 是网站页面、RSS（以及以后的 API）唯一的读入口，只读 published_items 投影表和 events、reports。
付费调用幂等，有预算熔断
llm_calls 表以 logical_key（任务 + 输入版本 + 模型 + 提示词版本）唯一。状态为 unknown 的调用不自动重发。AI Gateway spend limit 是硬上限，应用内每日预算检查是软上限。
安全阀只有设成 true 才打开
COLLECT_ENABLED、MODEL_CALLS_ENABLED、DISCOVERY_ENABLED、BROWSER_RUN_ENABLED、THIRD_PARTY_READER_ENABLED 默认关。测试只连本地假服务，不访问外部网络。
信源只展示摘要和原文链接
正文可以抓来做分析，保存方式见 Q14。页面上只展示摘要和原文链接。sources.fulltext 默认 0，只有来源明确允许时才展示全文。
公开内容匿名，后台只允许管理员
管理员和访客看到的公开页面一样。后台入口见问题 Q2。
05 · 系统组成

一个 Worker，三个入口

  • 为什么不拆多个 Worker：单管理员、规模小（见 Q8），一个 Worker 部署和回滚都简单。三个入口之间的边界靠目录和架构测试守，不靠进程。
  • Workflows 暂不用：每篇文章的步骤都能在一条 queue 消息里做完，幂等由 llm_calls 保证。信源发现若超出单次 15 分钟，再换成 Workflow。
  • 前端框架（Hono JSX SSR 还是 React Router）属于架构选型，scope 确认后再做跨家族评审。

D1 上的幂等与串行化靠什么

AIHOT 靠 Postgres 的 FOR UPDATE、advisory lock 和"事务内入队"。D1 没有这些，只有 batch()（原子性待核实）。ainews 的对应做法：

要保证的事AIHOTainews
同一篇文章不入库两次identity_key UNIQUEarticles.url_hash UNIQUE + INSERT … ON CONFLICT DO NOTHING
同一次模型调用不付两次钱receipts + FOR UPDATEllm_calls.logical_key UNIQUE：先插 pending，抢到的才调用；命中 completed 直接用结果
同一新事件不被建两次group 队列并发 1group 队列 max_concurrency: 1，同样的做法
写库和入队不丢enqueue(tx) 同事务D1 与 Queues 无共享事务：先写状态，再发消息；Cron 每 5 分钟补发卡在中间状态的条目
预算不超advisory lock 串行检查AI Gateway spend limit（最终一致，短时并发可略超）+ 入队前查当日已花费
07 · 正文抓取梯

从便宜到贵逐档试，每个信源记住能用的那一档

RSS 常常只给标题和一两句话，而 Brief、证据标签和以后的 Ask 都要正文。新信源批准时先探测一次，把最便宜的可用档写进 sources.fetch_rung。连续失败 3 次就重新探测。每篇文章记下实际用的档，作为溯源信息。

档做法成本限制与依据
0RSS 的 content:encoded 已带全文0只有部分信源提供
1fetch(url, {headers: {Accept: "text/markdown"}})，响应的 content-type 是 text/markdown 就直接用0只对开了 Markdown for Agents 的 Cloudflare 站点生效（Pro 及以上套餐），HTML 上限 6 MiB 已验证；新闻站里的命中率 未知
2fetch 拿 HTML，再交给 env.AI.toMarkdown()，可以用 cssSelector 只取正文文档原文：大多数格式免费不执行 JS 已验证
3第三方 reader：Jina r.jina.ai（Firecrawl 做备选）免费额度内为 0Jina：不带 key 20 RPM；新 key 送 1,000 万 token；带 key 的 RPM，表格写 500、FAQ 写 100，按 100 规划。Firecrawl：每月 1,000 credits，2 个并发。数字来自第三方页面 2026-10-22 的原文，可能变动。要抓的 URL 会发给第三方。开关默认关，见 Q13
4Browser Run env.BROWSER.quickAction("markdown", {url, gotoOptions: {waitUntil: "networkidle2"}})，渲染 JS 后转 MarkdownPaid 含 10 小时/月，超出部分 $0.09/小时compat date ≥ 2026-03-24；Paid 30 次/秒；超时 60 秒；Free 每 10 秒 1 次、每天 10 分钟；始终表明自己是 bot，不绕过反爬；响应头 X-Browser-Ms-Used 给出每次用时 已验证
  • Browser Run 能撑多少页：10 小时 = 36,000 秒。按每页 5 秒算，每月约 7,000 页不额外花钱。假设：每页 5 秒是估的，上线后用 X-Browser-Ms-Used 的实测值替换。
  • robots.txt：Browser Run 只有 /crawl 写明遵守 robots.txt，/markdown 文档没写；Jina 要显式开启。所以第 1–4 档统一由我们自己先读 robots.txt，被禁止就停下，并把信源标成"只用 RSS"。假设：/markdown 本身不检查 robots.txt。
  • 为什么第 3 档排在第 4 档前面：在免费额度内它不花钱。代价是多一个外部依赖，而且 URL 会交给第三方。如果你更在意只用 Cloudflare，Q13 选"不接"，梯子就变成 0 → 1 → 2 → 4。
  • 付费步骤：第 4 档和模型调用一样，用时记进 llm_calls 同一张账本（类型 browser），一起受每日预算约束。

10 · 平台约束

今天（2026-10-22）从 Cloudflare 官方文档查到的数字。标签：已验证 文档原文；推断 由已验证事实推出；假设 没查到，实现前要核实。

约束对设计的影响依据
Cron 的 CPU 时间：Free 10 ms；Paid 30 s（间隔 < 1 h）Free 上解析 RSS 都不够，必须 Workers Paid已验证
Queue consumer 单次 wall time 15 min；子请求 Paid 10,000/次一条消息做完一篇文章的全部步骤没问题已验证
Queues Free 每天 10,000 次操作，保留 24 h4 板块 × 40 信源 × 每 30 分钟 ≈ 7,680 次抓取/天，每条消息约 3 次操作，超过 Free推断
Browser Run：Paid 含 10 小时/月，之后 $0.09/小时；按天累计秒数、按月四舍五入到小时；因 waitForTimeout 失败的请求不计费第 4 档可以作为常规手段，不只是兜底已验证
Browser Run Quick Actions：Paid 30 次/秒，Free 每 10 秒 1 次；浏览器超时 60 秒；Worker 绑定 quickAction() 需要 compat date ≥ 2026-03-24Free 上第 4 档基本不能用，又一个必须 Paid 的理由已验证
Markdown for Agents：只在 Pro / Business / Enterprise 站点开启时生效，HTML ≤ 6 MiB第 1 档是"碰上了就省钱"，不能当主路已验证
Workers AI toMarkdown()：大多数格式免费，图片转换可能消耗 Neurons第 2 档只传 HTML，不传图片已验证
Jina Reader 带 key 的速率：同一页面上 500 RPM 和 100 RPM 两个数字矛盾按 100 RPM 规划，并用队列限流已验证（矛盾本身）
D1 单库 10 GB；Free 每天写 10 万行（2026-09-01 起超限即失败）；Paid 每月含 5,000 万行写只存摘要的话，单库够用多年；长期存正文会超限，见 Q14。Paid 写入额度充足已验证
